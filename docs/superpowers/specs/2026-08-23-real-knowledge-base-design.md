# AI Mall 真实知识库语料设计

## 目标

将当前以重复模板、随机地区和虚构编号扩写的“合成测试知识库”替换为可供 AI 客服实际引用的正式电商知识库，同时保留已有上传、摄取、分块、索引、检索和管理接口。

## 当前问题

- 当前生成语料标题带有“合成测试知识库”和“场景”字样，不适合作为客服答案来源。
- 单篇约 5.7 万字，主要依靠模板重复获得分块数量，命中结果可能被重复段落污染。
- `KB-xx-xx-xx` 等编号、随机地区和渠道差异没有稳定业务依据。
- 评测查询依赖虚构编号，验证的是模板识别而非真实用户问题的回答能力。

## 内容结构

语料保持 15 份左右、每份职责清晰的独立文档，覆盖：

1. 平台基础服务与账户规则
2. 下单、订单修改与取消
3. 支付、退款与资金到账
4. 发票开具与售后处理
5. 会员、积分、优惠券与价格保护
6. 普通快递、签收与物流异常
7. 同城配送、生鲜冷链与大件预约
8. 跨境订单、偏远地区及特殊物流
9. 七天无理由退货及例外商品
10. 质量问题、错发漏发与换货
11. 质保、维修与售后凭证
12. 投诉、举证、平台介入与申诉
13. 账户安全、隐私与风险控制
14. 数码、家电、服饰和美妆验收售后指引
15. 食品、母婴、运动、家居和汽车用品验收售后指引

## 文档规范

每份文档按适用情况包含以下章节：

- 适用范围
- 核心规则
- 办理条件
- 操作流程
- 处理时限
- 费用与责任承担
- 不适用或例外情形
- 所需凭证
- 常见问题

所有规则以现有 `platform-policies.md` 为事实基线。新增细化内容不得与其冲突；缺乏业务依据时使用明确、保守的表述，例如“以订单页展示或客服审核结果为准”，不虚构监管承诺、赔付金额或地区差异。

## 数据与接口

- 保留 `DocumentSpec`、`build_dataset()` 和 `write_dataset()` 入口，避免修改播种服务与部署流程。
- 文档 key、标题和文件名改为稳定的业务语义名称，不再使用 `synthetic-kb-*`。
- Manifest 继续提供 `key`、`title`、`docType`、`fileFormat`、`resource`、`topic`、`evalTags`、`charCount` 和 `estimatedChunkCount`。
- 正式种子文档统一使用 UTF-8 Markdown；不再为格式覆盖而制造信息损失的 ASCII PDF。管理员仍可上传 PDF/TXT，原有格式支持不变。
- 生成前清理输出目录中旧生成文件，避免已移除文档继续被打包或误播种。

## 检索评测

- 每份文档至少对应一个自然语言问题。
- 问题覆盖直接询问、口语改写、条件例外、多步骤办理、时限和相邻主题区分。
- `must_hit` 使用文档中的真实规则短语，不使用虚构编号。
- 测试验证文档 key/标题/主题唯一、禁止词不存在、清单资源真实存在、评测答案确实出现在目标文档中。

## 错误处理

- 输出目录无法写入时沿用 Python 文件异常，不吞掉错误。
- 非法文档数量不再作为公开配置；正式语料固定由目录定义。
- 文档内容为空、标题重复、评测答案缺失时由测试和生成前校验立即失败。

## 测试与验收

- 先修改测试，使其要求正式标题、真实主题、Markdown 格式和自然语言评测，并确认旧实现失败。
- 最小实现通过脚本单元测试后重新生成 Manifest、文档和 JSONL 评测集。
- 检查所有生成文档非空、无“合成测试”“场景编号”“KB-”等合成痕迹。
- 运行相关 Python 测试；若环境允许，再运行后端知识库测试验证播种清单兼容性。

## 范围边界

本次不修改向量库、分块算法、管理页面、上传接口或聊天提示词；不新增依赖，也不追求通过重复内容凑到固定分块数量。后续只有在真实召回评测显示覆盖不足时，才新增独立业务文档或补充规则。
