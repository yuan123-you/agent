# Pure-local small-model latency follow-up

**Goal:** Reduce uncached local inference input/decode work without cloud inference, smaller models, answer truncation or loss of evidence/business safeguards.
**Architecture:** Project retrieval facts into model inputs; keep verified long source URLs outside inference and attach them programmatically after streamed answers. Remove UI-only product image metadata from inference copies, and use a concise product-consult prompt with unchanged tools and approvals.
**Execution:** Sequential TDD in the existing workspace, preserving unrelated concurrent changes. No deployment/model download/provider change/commit/push.

## Fresh baseline — actual existing local Ollama model, one diagnostic output token
- Identical real search evidence, distinct initial nonces to prevent prefix-cache reuse; four threads, batch 512:
  - raw tool messages: 649 prompt tokens, prefill 8.156s; load 2.837s; wall 11.024s.
  - facts-only projection (all titles/snippets retained): 426 tokens, prefill 4.927s; load 0.002s; wall 4.949s.
- Two threads worsened prefill to 8.637s. Batch 128 gave 5.057s, not an improvement over 512. Do not change those defaults.
- These are individual uncached-input microbenchmarks, not end-to-end/P95 promises. Keep both load and prefill visible rather than comparing cold wall time to warm wall time.

## Delivered changes
- `prompt_context.py` projects all web titles/snippets and supplemental fact fields into plain evidence. Validated source domains remain available; full source addresses stay in program-owned footers rather than being copied/generated by the model. Repeated source destinations share one reference number, without dropping any evidence passage.
- Source links are HTTP(S)-validated, credential-bearing/unsafe destinations are excluded, Markdown destinations are encoded and labels escaped. The terminal answer carries its owned footer in metadata; SSE appends it after model-text validation, once, for streaming and non-streaming paths.
- Product inference copies omit UI image transport fields for ordinary questions, retaining prices, stock, identifiers, specs, links and unknown business fields. Explicit image/hash/link questions and relevant recent context retain those original fields. Stored messages and tool-call IDs are unchanged.
- `PRODUCT_SYSTEM_PROMPT` replaces the full all-business prompt only for product consultation. Pure product turns bind search/detail; explicit/recent policy questions, recent actual KB evidence and RAG use retain policy retrieval. Explicit human requests retain their capability. Other business intent routes were not changed.
- Long-term memory inference reuses compacted assistant evidence without losing user facts. Its JSON extraction explicitly opts out of the classifier's 64-token limit; customer-facing answers also remain uncapped.
- Found that product freshness reads had already been parallelized by concurrent work. Did not modify or claim that work.

## Actual measurements
All live experiments used the existing local Qwen 1.5B/Ollama service, synthetic questions, public catalog/web records, and diagnostic-process-only source loading. No cloud model call, model replacement/download, server source/configuration update, database mutation, service restart or production deployment was performed by this task. End-to-end shadow requests used user ID 0 and an in-memory checkpointer, so these are not authenticated-user/background-memory/concurrency SLO measurements.

- Fixed-evidence CPU experiment (before final source-domain/query-specific information-preservation refinements): 649 → 426 prompt tokens; input prefill 8.156 → 4.927 seconds. Preserve the distinction between model load time and prefill, and do not call this a complete-response benchmark.
- Two projected-pipeline samples on the same question types as the preceding task: first real streamed text 13.436s / 11.632s; completed at 30.672s / 27.782s with coherent token/done content and source footers. Previous distinct-query samples were 22.799s / 21.148s to first text and unfinished at the diagnostic 60s limit. Search data and host load can vary; these are samples, not a controlled P95 estimate.
- Final-source single-question acceptance run: preload 7.517s before accepting the synthetic request; first real text 14.638s; complete at 26.055s. Semantic intent classification 2.153s, one real web lookup, one tool-free answer inference; source footer present and streamed content exactly matched `done.content`.
- Public-catalog one-output-token diagnostics: previous full prompt/four-tool request hit its 60s diagnostic read limit. Compact prompt with four tools measured 1,406 prompt tokens / 55.112s prefill; scoped two-tool sample measured 1,205 / 15.464s. These isolated stage samples may include load/cache/queue differences and must not be advertised as end-to-end shopping latency or a causal speed ratio.

## Limits / next acceptance boundary
This is a measurable pure-local improvement, not stable second-level responses for every question. A single local inference runner is still shared with other requests/background memory work. Real-user multi-turn scheduling and concurrent tail latency need separate acceptance measurement. Do not hide those limits using only cache-warm cases, an early static label, truncated answers or cloud inference.
