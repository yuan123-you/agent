# RAG quality evidence dataset and runner — 2026-11-01

## Status and scope

Implemented directly on `codex/native-agent-recovery`, without commits, branches,
worktrees, network calls, production access, or changes to application code.
Only the four requested evaluation/documentation paths are owned by this work.
Other concurrent working-tree changes are not part of this deliverable.

Execution sequence: inspect canonical resources and actual retrieval boundaries;
write failing metric/dataset/report tests; implement the independent runner;
add fail-closed corpus and HTTP contracts; run the offline evaluation suite.

**This is tooling and an AI-prelabelled dataset, NOT an actual live quality result.**
No measured model accuracy, SLA, or ablation improvement is claimed here. The
parent must run the explicitly opted-in read-only experiment later.

## Frozen dataset v1

- 27 independently authored Chinese questions: **20 positives, 6 negatives, 1
  unresolved**. None copies an existing evaluation question verbatim.
- Fixed dev split: 10 positives + 3 negatives; heldout: 10 positives + 3 negatives
  + 1 unresolved. Topic families are disjoint across splits. Paired questions
  within a family stay together; order is fixed, with no shuffle or tuning.
- All labels are **AI-prelabelled, NOT human-reviewed**. Queries and gold were
  written before retrieval outputs; no actual retrieval outputs were available
  during authoring. The split is a small group holdout, not a blinded human test.
- Positive evidence is exact text under a predeclared heading in the canonical
  `backend/src/main/resources/kbseed/platform-policies.md` resource, with source
  title, exact-evidence SHA-256 and entire-source byte SHA-256 per reference.
- Canonical source SHA-256:
  `488c2771be45bce23e60679647beea8e83c7b8daf872c37c9eb6188fc7ea2f55`.
- Dataset SHA-256:
  `e4bf545de03f37cc66a422217faf0d9930982bd5496b9b931ffd4b2a1e36c1e4`.

Topics cover simulated-payment boundaries, conditional return eligibility,
quality exchange, repair, exceptional goods, return/refund/exchange states,
rejection disputes, and evidence requirements. Demo limitations override older
unconditional/general-policy language. These are mall-resource labels, not legal
advice, externally verified statutory rights, or proof of completed transactions.

The latest **locally available public QA** reference inspected was
`docs/qa/2026-11-01-production-reranker.md`. Its facts reinforce manual review,

No external “latest” fact verification was performed: network access was forbidden.

### LF/CRLF deployment portability — 2026-11-02

The frozen dataset, gold labels, `source_sha256` and `text_sha256` values are
unchanged. The frozen source SHA above remains the original **raw-byte**
expectation, not a claim that every checkout has identical bytes. Git's LF blob
and a Windows CRLF checkout are accepted as representationally equivalent only
when the expected hash matches the actual bytes, their CRLF-to-LF variant, or
that variant rendered as CRLF. No whitespace trimming, BOM removal, lone-CR
normalization, content edits, or extra/missing final newline is allowed. Full
reference-corpus validation splits canonical-LF source text with the unchanged
splitter; published chunk contents, gold binding, metrics, gates and thresholds
remain strict and unchanged.

New live reports keep `provenance.reference_source_sha256` as the original
frozen raw expectations and add `provenance.reference_source_provenance`, keyed
by source path, with:

- `actual_sha256` and `reference_sha256`: actual checkout bytes and frozen raw
  expected bytes, respectively; these may legitimately differ.
- `actual_canonical_lf_sha256` and `reference_canonical_lf_sha256`: SHA-256 after
  replacing **only** CRLF with LF. The reference canonical hash is derived from
  the exact LF/CRLF variant that matches the frozen raw expectation, never by
  relabelling a raw hash. These canonical hashes must agree for acceptance.
- `match_mode`: `exact_bytes` or `lf_crlf_equivalent`; equivalent text is not
  presented as a byte-hash match.

Historical measured `2026-11-01-rag-quality-live.json` and
`2026-11-01-rag-quality-postcheck.json` remain untouched; these additional fields
apply only to newly generated live reports. No measurement is regenerated as
part of this portability fix.

Retry evidence **code-source** fingerprints now hash bytes with only CRLF
replaced by LF and explicitly publish `source_hash_mode: "utf8-lf"`. The strict
validator requires that mode and recomputes those hashes; missing/other modes
and real source changes fail closed. Existing evidence must be regenerated by
the parent after final source files are in place, not retroactively relabelled.
Only local/offline contracts and the existing loopback TCP fault tests are run;
there is no model, credential, production, or external-network access.

case for its deployed corpus, but the local generated seed includes
`generated/docs/invoice-service.md`. That disagreement does **not** justify an

Resolving it requires inspecting the actual published invoice source and a

The six negative cases concern out-of-domain questions or policies of external

## Gold integrity and environment mismatch

IDs 209, 223, 224, 226, 227, 242, 244 and 247 mentioned in earlier QA are
**deployment-specific observations**, not portable labels, and are not hardcoded
in this dataset or runner.

Before any query recall, live execution:

1. Reads the configured primary Milvus collection through a read-only scalar
   iterator, restricted to platform-wide `POLICY` chunks.
2. Checks chunk IDs through `BackendClient.kb_current_chunks`, retaining only
   current ACTIVE published versions and their backend-supplied titles.
3. Validates the **entire referenced document**, not just a matching sentence:
   the canonical file must match its frozen byte hash exactly or by the LF/CRLF
   representation-only rule below, and the multiset of full
   published chunk hashes must equal the canonical resource split with the
   unchanged deployed pure `split_text` function and chunk settings. The source
   title must identify one published document. No ingest/index/write function
   is called. Different text, chunk layout, duplicate documents, or missing
   vectorized chunks invalidates the experiment rather than being relabelled.
4. Resolves each reference by source title, heading, exact evidence and its hash.
   This mapping precedes and is independent of every ranked candidate pool.
5. Requires every recalled candidate's identity, metadata, text and source to
   match that snapshot. SQL NULL platform scope and vector `-1` are normalized
   as equivalent; product-specific candidates are rejected.
6. Re-reads and fingerprints the published corpus after evaluation. Any observed
   drift invalidates all quality aggregates; available raw partial cases remain
   in the failure report. Two snapshots cannot detect a change-and-revert
   between snapshots, so run against a quiescent published corpus.

A missing gold **source** is an environment mismatch, not zero recall. Once the
source is independently validated, failure to **retrieve** its relevant chunk
is legitimately zero recall. No reference is repaired from its model output.
A different production corpus needs a separately frozen, reviewed dataset or
source reconciliation, not ID substitution or post-output label tuning.

## Four arms and measurement contract

Per case, issue exactly one actual dense recall and one actual backend BM25
recall concurrently, using unchanged runtime recall sizes. Reuse those exact
pools for all arms:

1. `dense_only`: dense provider order, first four.
2. `bm25_only`: BM25 provider order, first four.
3. `rrf_hybrid`: actual application RRF over the same two pools, first four.
4. `rrf_http_reranker`: actual configured `QwenHttpReranker` HTTP client scores
   the entire same RRF pool, then takes four. The class name is the compatible
   wire protocol, not an assertion that the deployed weights are Qwen.

No generator, LLM judge, extra model, semantic keyword proxy, fake rerank,
transaction, user/session action, threshold calibration, corpus write, or
fallback ranking is part of the live experiment. The existing query embedding
factory is pinned to the indexed model. Disabled HTTP reranking, missing or
malformed scores, incomplete rankings, mismatched candidates, and failed HTTP
calls invalidate the run; they are never credited as a successful fine arm.
An entirely empty rerank workload cannot be reported as four-arm live evidence.

Provider ranking order is preserved even for rounded-score ties. Application
RRF uses its score/best-rank/chunk-ID tie break. The actual HTTP client preserves
RRF order for tied rerank scores. Deep copies prevent rerank mutation from
contaminating baseline pools. Queries/candidate text, not gold labels or expected
answers, cross the retrieval/reranker boundaries.

### Metrics and relevance vs answerability

Binary, chunk-level, macro-averaged **Recall@4**, **MRR@4**, **nDCG@4** are reported
for positives, separately by dev/heldout and pooled. Recall's denominator is all
independently resolved gold chunks, including those not recalled. DCG discounts
are `1/log2(rank+1)` and IDCG has `min(4, gold_count)` unit gains. An absent
positive ranking scores zero; an empty-gold case has null ranking metrics.
Multiple matching overlapping chunks are distinct chunk-level gold IDs, not a
single document-level gain.

Answerability uses the application's existing evidence normalization and
confidence/margin thresholds unchanged for each arm. Positive acceptance is
reported separately from ranking relevance. Negative false-accept and rejection
rates use negatives only, with their own counts. A genuinely relevant repair
source can score well on ranking while the confidence gate refuses it. Neither
case proves generated-answer correctness; no answer generation is performed.

### Latency and provenance

Reports contain raw per-case recalled pools, fused pools, final candidates,
all available scores, gold references/IDs, gate decisions and stage timings.
Distributions include every sample, count, p50, p95 (linear interpolation) and
max for dense, BM25, parallel recall wall time, fusion, HTTP reranking, case
wall time, and initial/final corpus reads. Dense includes the existing encoder,
Milvus search and current-version validation; those sub-stages are not isolated.
There is one fixed-order pass, no warmup, and no repeated-load statistics.

These stage samples are **not independent per-arm end-to-end latency trials**;
shared recall is measured once, not charged four times. Small-sample p95 is not
a latency SLA. Snapshot and local evaluation overhead are not inference latency.

Provenance records dataset/selection/implementation/source hashes, selected case
order, corpus/chunk hashes and source titles, gold bindings, public model/config
identifiers, scope, recall sizes, RRF settings, gate settings, Python version,
timestamp and label-review status. Application source hashes identify the code
loaded by this runner, not independently attested remote backend binaries.
Reranker/embedding weight hashes and served-model identity are **unverified**;
configured identifiers are not a weight attestation. The parent should retain
separately verified public deployment/model fingerprints alongside its report.
No credentials, tokens, environment dump or private deployment data is emitted.

## Running it

From the repository root, local validation only (stdlib; no app imports or network):

```powershell
$env:PYTHONDONTWRITEBYTECODE='1'
python -B -m eval.rag_quality
python -B -m pytest eval/tests/test_rag_quality.py -q -p no:cacheprovider
```

Default validation reports `dataset_validation_only`, `quality: null` and
`unresolved_ids: ["rq27"]`. It verifies local source hashes; it does not prove
that a deployment contains them.

**Explicit opt-in live run**, in its authorized server/runtime environment
with existing application dependencies/configuration and this checkout's
canonical sources available, after confirming read-only published-KB access:

```powershell
python -B -m eval.rag_quality --live --ack-read-only --exclude-unresolved
```

`--split dev` or `--split heldout` can select a fixed split; default is both.
`--exclude-unresolved` explicitly omits and reports `rq27`; without it the
all/heldout run fails before app imports or network access. It cannot exclude
missing resolved-positive evidence or silently turn unknown labels negative.

JSON is printed to stdout only; this runner never creates a report file. The
parent can capture stdout to a separately authorized artifact path. Check exit
status and JSON status, not just whether JSON exists: invalid/environment-mismatch
runs exit 2 with `quality: null`; only a fully successful real run yields
`measured_live`. Normal app configuration is imported only after live opt-in;
no credential files or deployment-private files were inspected during this work.
The tool has no credential-discovery, deployment, transaction, or chat interface.

Offline doubles and mocked HTTP transports are limited to contract tests.
Their reports are permanently labelled `offline_contract_only`, expose at most
`diagnostics`, and have `quality: null`; they are never model accuracy evidence.

## Verification and limits

- Initial TDD run: missing implementation produced failing tests before code.
- Targeted contracts cover hand-computed metric math, missing gold, malformed
  candidates, ties/duplicates, split leakage, exact canonical hashes,
  source-version/layout mismatch, drift, raw/provenance reporting, negative
  denominators, offline/live separation, and fail-closed unresolved labels.
- A synthetic HTTP-transport test exercises the **real** RRF implementation,
  HTTP client/request validation, rerank ordering and production gate while
  explicitly retaining offline-only reporting. No real request is sent.
- Snapshot contract verifies scalar reads and current-published filtering only.
- Original authoring offline eval suite: **49 passed**. One pre-existing pytest-asyncio/Python
  deprecation warning about `get_event_loop_policy` was emitted.
- 2026-11-02 portability fix: focused red run **7 failed, 9 passed,
  65 deselected**, then the two owned modules **81 passed**. Full local eval
  suite (`python -B -m pytest eval/tests -q -p no:cacheprovider`): **107 passed**,
  with the same single pytest-asyncio deprecation warning. No live run or new
  measured artifact was produced; only existing loopback TCP fault tests use
  sockets. Tests cover both frozen/actual LF and CRLF directions, preserve raw
  expectations, report canonical equivalence honestly, and refuse content,
  whitespace, BOM, lone-CR and extra-newline changes.
- No actual server benchmark was run during dataset/tool authoring. The later
  parent-run, read-only 2026-11-01 experiment is preserved separately in
  `2026-11-01-rag-quality-live.json` and summarized in
  `2026-11-01-native-agent-recovery.md`; it did not change this dataset or gold.
  It passed full-source/corpus-drift validation, excluded unresolved `rq27`, and
  scored 260 real query-document pairs. Its low positive answerability is an
  explicit limitation, not a reason to revise heldout labels after measurement.

Limitations: 20 positive labels cover one canonical policy document and are not
an exhaustive relevance adjudication across all generated or future KB sources.
Other chunks may be genuinely relevant but unlabelled: these are silver labels,
not a complete human relevance set. The small family-heldout sample shares its
source document with dev and is not independent-document generalization. Six
negative cases cannot establish broad rejection safety. Full-source matching is
intentionally strict and may reject a legitimate differently chunked deployment.
Manual source reconciliation and human review must precede stronger conclusions.
Do not tune gold, thresholds, wording or heldout selection after seeing outputs.
