### 1.2 数据面与控制面说明

- **数据面（用户请求链路）**：浏览器 → Vue 前端 → 后端（鉴权/校验/持久化）→ AI 服务（Agent 编排）→ LLM / Milvus → 原路 SSE 流式返回（含内联链接文本）→ 前端渲染高亮链接。
- **控制面（管理链路）**：商品管理、订单管理（发货）、用户管理均只操作 MySQL；仅「知识库文档摄取」触发后端 → AI 服务的异步任务。

## 2. 各层职责划分与交互关系

### 2.1 ① 前端层（frontend）

| 职责 | 说明 |
|------|------|
| UI 渲染 | 买家端（AI 对话、商品、订单）、客服工作台、管理后台 |
| SSE 消费 | 基于 fetch 流式解析（EventSource 不支持 POST + Header），按五类事件分发 |
| **内联链接渲染** | 解析 AI 回答中的 `[文本](mall://…)` 标记，渲染为高亮可点击文字，点击 router.push 跳转 |
| 状态管理 | Pinia：auth / chat / product / order / kb 等 store |
| 禁止事项 | **永不直连 Python 服务或 LLM 供应商**；不在前端保存任何密钥 |

### 2.2 ② 后端服务层（backend）

| 职责 | 具体实现 |
|------|---------|
| 用户认证 | Spring Security 6 + JWT（登录签发、过滤器校验、Redis 黑名单登出） |
| 授权 | RBAC 三角色（ADMIN/AGENT/CUSTOMER）；user_id 从令牌解析后强制注入查询条件 |
| 参数校验 | Bean Validation（@Valid + 全局异常处理器） |
| 电商业务 | 商品 CRUD/上下架、下单（模拟支付）、订单状态流转（发货/取消）、库存扣减 |
| 消息持久化 | 会话、消息（含 AI 工具调用记录与链接原文）落 MySQL；会话热数据缓存 Redis |
| 限流 | Redis + Lua 令牌桶：登录防爆破、每用户对话 QPS |
| 熔断 | Resilience4j CircuitBreaker 包裹对 AI 服务的调用 |
| SSE 代理 | WebClient 非阻塞订阅 AI 服务 SSE → 逐事件转发给前端 SseEmitter |
| SSE 生命周期 | Emitter 注册表；onCompletion/onTimeout/onError 主动移除，防内存泄漏 |
| 工具回调 API | 暴露 `/internal/tools/**` 供 AI 服务执行「商品检索/订单查询/AI 下单/转人工」等业务动作（仅内网 + 内部令牌） |

### 2.3 ③ AI 推理服务层（ai-service）

| 职责 | 具体实现 |
|------|---------|
| LLM 推理 | LangChain 1.x ChatModel（OpenAI 兼容接口） |
| Agent 编排 | LangGraph StateGraph：意图路由 → 工具循环（商品检索/RAG/订单工具）→ 流式回答 |
| 工具执行 | LangGraph ToolNode；业务动作经 HTTP 回调后端 |
| 向量检索 | Milvus：知识分块向量入库、相似检索、标量过滤（product_id / doc_type / doc_version） |
| RAG 链路 | 文档摄取（解析→分割→Embedding→入库）+ 查询（检索→重排→注入上下文） |
| **链接生成** | System Prompt 约束：回答提及商品/订单时必须使用 `[名称](mall://product/{id})` 内联链接语法，且 id 只能来自工具结果 |
| SSE 输出 | FastAPI StreamingResponse，事件类型：token / tool_call / tool_result / error / done |
| 无状态 | 不存储会话；上下文由后端每轮请求显式传入；多实例可水平扩展 |

**AI 服务禁止事项（红线）**：不做用户鉴权、不直连 MySQL 业务库、不直接暴露给前端。

### 2.4 交互关系矩阵

| 调用方 → 被调方 | 协议 | 方向与内容 |
|----------------|------|-----------|
| 前端 → 后端 | REST + SSE | 全部业务请求、AI 对话流 |
| 后端 → AI 服务 | HTTP + SSE（WebClient） | `/v1/chat/stream` 对话流；`/v1/kb/ingest` 文档摄取 |
| AI 服务 → 后端 | HTTP（内部令牌） | `/internal/tools/**` 业务工具回调（商品检索/查订单/下单/转人工） |
| AI 服务 → Milvus | gRPC（pymilvus） | 向量 CRUD 与检索 |
| AI 服务 → LLM | HTTPS（OpenAI 兼容） | Embedding + Chat |
| 后端 → MySQL | JDBC（MyBatis-Plus） | 业务数据唯一写入方 |
| 后端 → Redis | Lettuce | 缓存/限流/黑名单 |

### 3.2 关键备选方案对比（为什么这样选）

| 决策点 | 备选 | 结论与理由 |
|--------|------|-----------|
| 向量库 | Milvus / Qdrant / pgvector | **选 Milvus**：标量过滤（product_id/doc_type）与生产级性能兼备，standalone 部署简单 |
| Agent 编排 | LangGraph / AutoGen / CrewAI | **选 LangGraph**：显式状态图、可控性强、工具循环原生支持；多 Agent 对话框架对本场景过重 |
| 内联链接格式 | 自定义标记 `{{link:id\|text}}` / Markdown 链接 | **选 Markdown 链接 `[文本](mall://…)`**：LLM 对 markdown 熟悉生成稳定；前端 marked 自定义 renderer 天然支持拦截自定义 scheme |
| SSE 客户端（前端） | EventSource / fetch | **选 fetch + ReadableStream**：EventSource 不支持 POST 与 Authorization 头 |
| 后端调 AI | WebClient / RestTemplate / OpenFeign | **选 WebClient**：RestTemplate 同步阻塞无法消费无限流。**禁止 RestTemplate** |
| 商品检索 | 向量检索商品 / SQL 结构化查询 | **选 SQL（后端回调）为主 + RAG 补充卖点**：价格/类目/库存是结构化约束，SQL 精确；商品介绍/评测等非结构化内容走 RAG。混合才能兼顾准确与语义 |

## 4. 核心数据流：一次完整请求的全链路流转

以买家发送「推荐一款 3000 以内拍照好的手机」为例：

```
[1] 前端
    POST /api/v1/chat/messages  (Authorization: Bearer <JWT>)
    body: { conversationId, content: "推荐一款3000以内拍照好的手机" }
    → fetch 流式读取响应

[2] 后端：前置处理（同步，<50ms 目标）
    2.1 JWT 过滤器：校验签名/过期/黑名单 → 解出 userId、role
    2.2 参数校验：conversationId 归属校验（防越权）
    2.3 限流：Redis Lua 令牌桶（每用户对话 20 次/分钟）
    2.4 落库用户消息 message(role=USER)
    2.5 组装上下文：最近 N 轮消息 + 会话摘要 + 用户画像

[3] 后端 → AI 服务：SSE 代理建立
    3.1 创建 SseEmitter 并注册 EmitterManager
    3.2 WebClient POST http://ai-service:8000/v1/chat/stream
        headers: X-Internal-Token
        body: { conversation_id, user_id, message,
                history: [...], summary, user_profile: {...} }
    3.3 订阅响应流 Flux<ServerSentEvent>

[4] AI 服务：LangGraph 执行
    4.1 意图识别节点 → 商品推荐意图
    4.2 工具调用：product_search(maxPrice=3000, keyword="拍照")
        → 回调后端 /internal/tools/product/search
        → 后端 SQL 检索（上架、价格约束、库存>0）→ 返回商品列表
        → tool_result 事件（含商品 id/name/价格/卖点）
    4.3 （可选）kb_search 检索商品评测/亮点 → tool_result 事件
    4.4 respond 节点流式生成：
        "为您找到 3 款：1. [星耀 X5 Pro](mall://product/1001)…"
        （逐 token 事件，链接语法内嵌在 token 流中）
    4.5 输出 done 事件（含 token 用量、耗时）

[5] 后端：事件透传与收尾
    5.1 逐事件转发给 SseEmitter（事件类型不变，链接原文随 token 透传）
    5.2 done 事件到达 → 落库 AI 完整消息（content 含链接原文 + tool_calls JSON）
    5.3 Emitter 完成 → 注册表移除

[6] 前端：流式渲染 + 链接跳转
    6.1 token 增量追加 → marked 渲染（节流）
    6.2 自定义 renderer 拦截 mall:// 链接 → 高亮 span（data-route）
    6.3 流式中未闭合的 "[" 片段由缓冲器暂存，避免闪现半截标记
    6.4 用户点击"星耀 X5 Pro" → router.push('/products/1001')

[7] 异常路径
    - AI 服务超时/5xx → CircuitBreaker 记录 → error 事件 + 降级话术
      （"AI 助手繁忙，您可以先逛逛商品列表，或稍后再试"）
    - 前端断开 → emitter 清理 + 上游订阅取消
```

## 5. 关键设计决策（Why）

### D1：为什么三层隔离，前端永不直连 AI 服务？

1. **安全**：LLM API Key 必须留在后端；AI 服务无鉴权能力，暴露即裸奔。
2. **可控**：后端统一限流、审计、行级数据校验，AI 服务专注推理。
3. **可替换**：未来更换 Agent 框架或多模型路由，前端零改动。

### D2：为什么 AI 工具回调后端而不是直连 MySQL？

商品检索（价格/库存/上架状态）与订单查询（归属校验、状态流转）是强业务规则，若 AI 服务直连库会绕过校验并造成规则双实现。**回调后端内部 API** 使业务规则只有一份实现，且后端在回调处二次强制注入 userId（不信任模型生成值），是越权防护的最后防线。

### D3：为什么商品检索用 SQL 工具而不用纯向量检索？

"3000 以内" 是硬性数值约束，向量检索只能"语义相似"无法精确过滤，会推荐 3500 元的手机；而"拍照好" 是语义描述，SQL LIKE 又无能为力。因此**结构化条件走 SQL（product_search 回调）、语义卖点走 RAG（kb_search 本地）**，二者结合是电商导购准确性的关键。

### D4：为什么内联链接选 Markdown 语法 + 自定义 scheme？

1. LLM 对 markdown 链接语法生成准确率高（训练语料天然熟悉）；
2. `mall://` 自定义 scheme 与外链 `http(s)://` 天然区分，前端 renderer 只放行白名单 scheme，防止 Prompt 注入让 AI 输出恶意外链被点击；
3. 落库原文即 markdown，历史消息重新渲染无需二次转换。

### D5：为什么 AI 服务无状态、上下文由后端传入？

1. 水平扩展无需会话粘滞（任意实例处理任意请求）。
2. 消息持久化唯一写入方是后端，避免双写不一致。
3. 会话摘要（长记忆压缩）由后端维护并随请求传入，AI 服务不落任何存储。

### D6：为什么 SSE 事件必须区分类型？

`token/tool_call/tool_result/error/done` 五类事件支撑：流式文本（token）、过程可视化（tool_*，增强可信度）、可观测与计费（done 携带 token 用量）。链接原文随 token 流透传，无需额外事件类型。

### D7：为什么用 WebClient 而非 RestTemplate 消费 SSE？

RestTemplate 同步阻塞，消费无限长 SSE 流会长期占用容器线程；WebClient 基于 Reactor，少量事件循环线程支撑数千并发流。

## 6. 扩展性设计

### 6.1 水平扩展

| 服务 | 扩展方式 | 说明 |
|------|---------|------|
| ai-service | 直接加实例（无状态） | LB 轮询；上下文由请求携带 |
| backend | 加实例 | JWT 无状态；限流计数在 Redis；SSE 长连接经 LB 需 ip_hash 或单层部署 |
| Milvus | standalone → cluster | pymilvus URI 不变 |
| MySQL | 读写分离 | 演进时引入动态数据源 |

### 6.2 组件替换方案

| 组件 | 替换目标 | 改动面 |
|------|---------|--------|
| LLM 供应商 | OpenAI → DeepSeek/Qwen | 仅改 AI 服务 .env 的 BASE_URL/MODEL/API_KEY |
| 向量库 | Milvus → Qdrant | 仅改 AI 服务 VectorStore 实现层 |
| Embedding 模型 | 换供应商 | .env 配置 + 全量重建索引脚本 |
| 消息推送 | SSE → WebSocket | 仅前端封装层与后端 Emitter 层 |

### 6.3 功能演进路线

- 购物车/优惠券（P2）：纯后端业务，AI 服务不动；
- AI 多模态（图片搜同款）：对话消息表已预留 image_url 字段；
- 渠道扩展（小程序/App）：替换前端壳，后端与 AI 服务不动。
